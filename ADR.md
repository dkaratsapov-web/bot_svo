# ADR — Значимые архитектурные решения

## ADR-001. Библиотека для MAX Bot API — `maxapi` (Python)

**Статус:** принято.

**Контекст.** ТЗ допускает два варианта: Python-библиотека `maxapi` (PyPI) или
официальная `@maxhub/max-bot-api` (Node/TypeScript). По умолчанию — Python.

**Решение.** Используем `maxapi==1.2.1`.

**Обоснование.**
- aiogram-подобный API (`Bot`, `Dispatcher`, `Router`, FSM, фильтры,
  middleware) точно ложится на требования ТЗ и весь остальной стек — Python
  (SQLAlchemy, Alembic, pydantic-settings, structlog).
- Встроены нужные типы кнопок: `CallbackButton`, `RequestContactButton`,
  `LinkButton`; событие `message_callback` и подтверждение через `send_callback`
  (POST /answers).
- Поддержаны оба режима получения обновлений: long polling (dev) и webhook
  (aiohttp-интеграция, проверка секрета `X-Max-Bot-Api-Secret`).
- FSM-хранилища из коробки: `MemoryContext` (dev) и `RedisContext` (prod).
- Базовый домен API — `https://platform-api2.max.ru`, совпадает с ТЗ; при
  необходимости переопределяется через `bot.set_api_url(API_BASE_URL)`.

**Последствия / риски.**
- Зависимость от стабильности стороннего пакета. Митигируется тонким слоем
  адаптации: тексты, клавиатуры, валидаторы, бизнес-логика и слой БД не зависят
  от внутренностей `maxapi` и покрыты тестами. При необходимости замену
  библиотеки можно локализовать в `handlers/*`, `keyboards.py`, `main.py`.
- Версия зафиксирована в `requirements.txt` во избежание неожиданных
  breaking-changes.

## ADR-002. Генерация тикетов без отдельной таблицы-счётчика

**Статус:** принято.

**Решение.** Порядковый номер тикета вычисляется как `max(...)+1` по
существующим тикетам для пары (префикс, год); формат с нулевым дополнением до
6 знаков обеспечивает корректную лексикографическую сортировку.

**Обоснование.** SQLite сериализует запись; тикет генерируется в той же
транзакции, что и вставка. Это проще отдельной таблицы счётчиков и достаточно
для одного инстанса. При переходе на несколько инстансов/иную СУБД —
заменить на таблицу-счётчик или sequence (точка изменения локализована в
`repo._next_ticket`).

## ADR-003. Идемпотентность и FSM-состояние в Redis

**Статус:** принято.

**Решение.** Дедупликация webhook-апдейтов — через `SET NX EX 24h` в Redis
(`IdempotencyStore`), FSM — `RedisContext`. В dev при пустом `REDIS_URL`
используются in-memory аналоги.

**Обоснование.** Требования ТЗ: незавершённые анкеты не теряются при
перезапуске (FSM в Redis), повторная доставка апдейта не создаёт дубль
(idempotency, TTL 24 ч).
